# Routing engines: node-level stop costs and turn costs, with a hands-on BRouter "flow" profile

## Question

Which open-source routing engine can (1) do road-bike routing with a customisable cost profile, (2) apply node-level costs (signals, stop, give-way, roundabout entry) and turn costs (right turns across traffic; Ireland drives on the left), (3) accept externally derived per-node / per-way stop probabilities (dhy.11 output), (4) return elevation-aware routes and (5) run cheaply self-hosted for a one-country graph? This picks the engine for a thin-slice "flow" spike.

## Hands-on check

All downloads are under gitignored `data/brouter/`. Reproduce:

```
scripts/run_brouter.sh setup                 # tiles + release zip + copies profiles/flow.brf next to stock profiles
scripts/run_brouter.sh serve &               # java -Xmx1g ... btools.server.RouteServer ... port 17777
scripts/run_brouter.sh route [outdir]        # writes the four GPX files (default data/samples/)
pkill -f btools.server.RouteServer
# events for the scorer (once; ~2.5 min) then score:
uv run scripts/osm_stop_features.py data/osm/ireland.osm.pbf --bbox=-6.6,52.95,-6.0,53.4 \
  --csv /tmp/s.csv --full-csv /tmp/f.csv --signals /tmp/sig.csv --causes-csv data/osm/events_dublin_wicklow.csv
uv run scripts/score_route_stops.py data/samples/brouter-*.gpx      # ~75 s (PBF scan dominates)
```

**Deviation: pre-built segments, not a local build.** BRouter's rd5 files were downloaded from https://brouter.de/brouter/segments4/ (`W10_N50.rd5` covers lon -10..-5, lat 50..55, so all of the Republic and NI south of 55 N; `W10_N55.rd5` the NI north coast; both Last-Modified 2026-10-20 01:03 GMT; 43,155,455 and 5,517,791 bytes) instead of building from `data/osm/ireland.osm.pbf`. The official procedure (osmosis pbf split, then `mapcreator` per 5x5 degree tile) is in https://github.com/abrensch/brouter/tree/master/misc/scripts/mapcreation and was not run; so build time is none (download ~10 s) and the tiles' OSM date is the brouter.de weekly date, not the Geofabrik extract used elsewhere (small risk of tag drift between the scoring PBF and the routing data). Release: https://github.com/abrensch/brouter/releases/tag/v1.7.10 (`brouter-1.7.10.zip`, the `-all.jar`). Java 21 existing install; nothing installed.

**Routes** (BRouter, lonlat order; `profile=fastbike` baseline vs `profile=flow`): Wicklow = Laragh (-6.2957,53.0112) -> Sally Gap (-6.3088,53.1358) -> Enniskerry (-6.1706,53.1928); Dublin fringe = Rathfarnham (-6.2825,53.2990) -> Glencullen (-6.2150,53.2210) -> Stepaside (-6.2110,53.2560). Coordinates were not verified against Nominatim; the routes snapped sensibly and no waypoint was flagged off-road.

**Flow profile** (`profiles/flow.brf`, copy of stock `fastbike.brf`, edits marked `FLOW`). Cost units are approximately metres of equivalent distance:
- node context `initialcost`: `traffic_signals` 300 (stock: 20), `crossing=traffic_signals` 150, `stop` 150, `give_way` 80, `mini_roundabout` 80.
- roundabout entry: not possible in node context (it sees only node tags). Done in way context with classifiers `1` = ordinary way, `2` = `junction=roundabout|circular`, `3` = ferry, and `initialcost = 150` on roundabout ways. **Source behaviour** (OsmPath.java line 159, https://github.com/abrensch/brouter/blob/master/brouter-core/src/main/java/btools/router/OsmPath.java): the new way's `initialcost` is charged only when both the previous and the new classifier are non-zero and they differ. My first version used classifier 0 for ordinary ways, so the roundabout cost never fired (the profile guide's "any change adds initialcost" is not what the code does); fixed by giving every way a non-zero classifier. **Verified**: re-routing the Dublin pair with `format=geojson` shows `InitialCost=150` on exactly one segment, at the roundabout entry near (-6.28426, 53.27792), and 0 elsewhere (route total 150; GPX `cost` 40522 -> 40672). The route did not change (the entry is unavoidable at that cost), so the before/after numbers are identical to the first run. Side effect: stock `fastbike` uses classifier 0 for ordinary ways and 1 for ferries, so by the same rule its ferry `initialcost 10000` very probably never fires either (not tested).
- signals are priced regardless of bike access (as stock); stop/give-way/mini-roundabout only apply to bike-accessible nodes.
- turns: stock `turncost=90` (0 on roundabouts) raised to 150. BRouter applies `(1 - cos(angle)) * turncost`, symmetric left/right, so a right turn costs the same as a left turn of the same angle. **BRouter cannot penalise right turns specifically**; this is the confirmed limit (source line cited above; behaviour consistent with measured right-turn counts below, unchanged by the profile).

**Scoring** (`scripts/score_route_stops.py`). Imports nothing from `osm_stop_features.py`; instead the dhy.10 script was extended (additive, default behaviour unchanged) with `--causes-csv`, which logs each event (way, direction, vertex, node, cause, amount) as the rule produces it, so the classification (explicit tags, 1b approach attribution, roundabout entry, inferred yield, 0.5 equal-class) is exactly dhy.10's, not re-derived. The scorer snaps GPX points to OSM vertices (STRtree, EPSG:2157, 5 m), fills the gaps left by BRouter's collinear-point thinning (way-sharing vertices, else local Dijkstra; 0 unfilled gaps), and sums the events hit on arrival at each vertex. Right turn = clockwise heading change in [+30, +150] degrees (10 m look-back/ahead) at a node shared by >= 2 road-class ways, not on a roundabout. Distances equal BRouter's own `track-length` (18.60 vs 18.607 km).

**Before/after** (baseline = stock `fastbike`, after = `flow`):

| Wicklow (Laragh-Sally Gap-Enniskerry) | fastbike | 37.92 | 8.0 | 0.21 | 0.00 | 0.00 | 0.16 | 9 | 1 | 491 / 454 |
| Wicklow | flow | 37.92 | 8.0 | 0.21 | 0.00 | 0.00 | 0.16 | 9 | 1 | 491 / 454 |
| Dublin fringe (Rathfarnham-Glencullen-Stepaside) | fastbike | 18.60 | 55.5 | 2.98 | 0.97 | 0.81 | 0.99 | 8 | 11 | 334 / 313 |

Reading: on the Dublin pair the flow profile cuts expected stops/km by 23% (2.98 -> 2.29; -11.5 expected stops) for +3.5% distance (+0.65 km) and +5 m ascent. The Wicklow route is unchanged because it passes essentially no stop-cause nodes (0.21 stops/km, all from the 0.5 equal-class rule, which the profile does not price) and no alternative within the cost range avoids more; "flow" has nothing to improve on a rural route, as expected. Right turns are unchanged in both (9 and 8): confirms the turn penalty has no handle on direction; at 0.43 right turns/km in the Dublin fringe and 0.24/km in Wicklow, the unpriced right-turn component is of the same order as the stop component there (8 right turns vs 44 expected stops), so a direction-aware turn cost would matter in town and little in the hills. Caveats: the expected-stops figures use the dhy.10 heuristics (the 0.5 equal-class rule is ~1/3 of the Dublin total and is not priced by the profile); no empirical validation here (dhy.11); the scorer was checked only through these four routes (no unit tests, no comparison against a hand-traced route); the node-cost weights (300/150/80) are untuned guesses.

**Retuned weights (planner epic).** `profiles/flow.brf` node costs were retuned to the validated weights in `stop-model-validation.md`: `traffic_signals` 300, signalled crossing 300 (was 150), `give_way` 80, `stop` 60 (was 150), `mini_roundabout` 80 and the roundabout-entry workaround 150 unchanged (both under-powered in the data). Every stop-cause node cost (not the footaccess penalty or the roundabout-entry way cost) is multiplied by a new global `flow_scale` (default 1.0). BRouter 1.7.10 RouteServer accepts per-request overrides of profile variables as `&profile:<var>=<value>` (verified: `&profile=flow&profile:flow_scale=0.5` / `2.0` / `5` give different routes, 18.60 / 20.11 / 20.16 km vs 18.41 km default on the Dublin pair), so `flow_lo` (0.5) and `flow_hi` (2.0) are the same profile with a URL override, not separate files; `scripts/run_brouter.sh route` emits all variants. Reference scorer (`--events data/osm/events_ireland.csv`):

| route | profile | km | expected stops/km | signals/km | xing-signals/km |
|---|---|---|---|---|---|
| Dublin fringe | fastbike | 18.60 | 2.98 | 0.97 | 0.81 |
| Dublin fringe | flow_lo (0.5) | 18.59 | 2.47 | 0.70 | 0.54 |
| Dublin fringe | flow (1.0) | 18.40 | 2.28 | 0.65 | 0.43 |
| Dublin fringe | flow_hi (2.0) | 20.12 | 1.37 | 0.25 | 0.15 |

Stops/km fall monotonically fastbike -> flow_lo -> flow -> flow_hi on the Dublin pair; flow_hi buys a 46% cut in stops/km for +8% distance. Wicklow routes are identical in all four (no stop-cause nodes to avoid). Note the earlier flow route was 19.25 km / 2.29 stops/km with the untuned weights; the retuned default is shorter (18.40 km) at the same stops/km because signalled crossings now cost 300.

### Integration path for dhy.11 per-node stop probability

**BRouter.** Pre-build only. With pyosmium, rewrite the Ireland PBF so each stop-cause node carries a tag, e.g. `stop_prob=6` (bucket index 0-10, i.e. probability rounded to 0.1), and add `stop_prob;<count> 0 1 2 ... 10` lines to the node section of a copy of `lookups.dat` (tag values must be enumerated in the lookup table; a float string like `0.63` would not be recognised, so it has to be bucketed; the profile arithmetic can then convert the bucket to cost, e.g. `multiply 30 stop_prob`). Then rebuild the rd5 tiles with `mapcreator` using that `lookups.dat` and use a profile whose node `initialcost` reads `stop_prob`. This means the pre-built brouter.de tiles used here cannot be reused for that step; a local build (not done here) becomes mandatory. A per-way score (e.g. stops/km) goes the same way as a way tag and is read in way `costfactor`. Not tested.

**GraphHopper.** Also pre-build: write the score as an OSM tag (`stop_prob=0.63` on the node, or aggregated onto the approach way as `stop_cost=...` because GraphHopper has edge, not node, costs), add a Java `TagParser` that fills a `DecimalEncodedValue` (floats are usable up to the configured bits and factor, e.g. 5 bits at 0.05 steps), register it via `graph.encoded_values` and reference it from the custom model (`"if": "stop_cost > 0.5", "multiply_by": ...` or `limit_to`/`add`-style terms; the model is posted per request, so weights are tunable at runtime without a rebuild, only the data needs the import). Needs a small custom Java build; not tested.

## Verdict

**Usable with caveats. Recommended for the thin-slice spike: BRouter.** It is the only engine here I got running end to end on Irish data in under an hour: node-level costs for signals/stop/give-way were expressible directly in the profile and demonstrably changed the route (-23% expected stops/km on the dense Dublin pair for +3.5% distance), elevation and GPX are built in, resources are tiny (270 MB RSS, sub-second routes), and the licence is MIT. Its limits are real: no left/right distinction in turn cost (confirmed in source and in the unchanged right-turn counts), no node-context visibility of way tags (roundabout entry needs the way-context classifier workaround, which I verified fires: InitialCost=150 at the one entry on the Dublin route), and score injection means a local rd5 rebuild with a custom `lookups.dat` and bucketed values. **Runner-up: GraphHopper** (Apache-2.0, per-request custom model, numeric encoded values, elevation, alternatives and round trip), at the price of Java work for any node-level cost; OSRM expresses stop obstacles and signed-angle turn costs best but has no elevation, which rules it out for this planner unless used only as a turn-cost reference. Valhalla exposes no stop/signal cost knob for bicycle in its documentation. Not measured: GraphHopper/Valhalla/OSRM runs, RAM, build times (time-boxed; docs-based only).
